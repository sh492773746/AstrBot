# Gemini gateway deployment: 2026-09-28

## Active topology

- Production controller plugin: v0.5.1. Production AstrBot PID 2478178 was not
  restarted; only its controller plugin was disabled/reloaded for the DB move.
- The sole authoritative business DB is now
  `/var/lib/astrbot-tenant-state/control.db`, root:astrtenant-state 0660, in a
  setgid 2770 directory. The controller's private `runtime.json` points here.
  Old controller DB paths are historical copies, not writable runtime inputs.
- Gateway: `astrbot-tenant-gateway.service`, enabled and running as `astrgateway`,
  group `astrtenant-state`, with no Docker group membership or capabilities.
  It cannot read the production data directory or access the Docker socket.
- Bind: `172.17.0.1:18734`. No domain, public interface binding or published
  Docker port. A narrow UFW rule allows only docker0 traffic from 172.17.0.0/16
  to 172.17.0.1 TCP 18734. Other firewall rules were not changed.
- Clients in the default Docker bridge can use
  `http://host.docker.internal:18734/v1` with the host-gateway mapping.

## Approved model and credentials

The gateway snapshots production provider `Gemini/gemini-3.8-flash`, resolving
its `provider_source_id=Gemini` source. The referenced source uses an
OpenAI-compatible HTTPS API. It is not a model installed inside AstrBot.
The gateway fixes the requested model to `gemini-3.8-flash`.

The upstream key is in `/etc/astrbot-tenant-gateway/gateway.json`, root-only 0600
under a 0700 directory, delivered via systemd `LoadCredential`. It is not in
command arguments, ordinary environment variables, plugin config or tenant data.
The gateway holds no Fernet key or Telegram token in plaintext. It can access
the trusted shared business DB for token-hash authorization and usage counting;
it is therefore a trusted backend, not an untrusted tenant process.

Only `/v1/chat/completions` is exposed. Embeddings and other AI routes were not
enabled. VIP's automatic AI-response switch remains off. Key/provider changes
in the production AstrBot config require a reviewed snapshot refresh and gateway
restart; they do not automatically change a running gateway.

New tenant default quota is 100 requests per UTC calendar month, snapshotted
at creation. Existing tenant entitlements are not rewritten. Attempts that reach
the upstream consume quota even if the upstream fails. Request size and output
bytes are bounded; max_tokens is capped in the outgoing request. These are
request-based safeguards, not a hard monetary spending cap or a guarantee about
an external provider's accounting for reasoning tokens.

## Acceptance

- One minimal direct upstream probe returned HTTP 200 and a valid response for
  `gemini-3.8-flash`.
- Live gateway health and unauthenticated/invalid-key checks returned 200,
  401 and 403 respectively.
- A disposable gateway instance with a separate temporary DB performed one
  actual upstream request. Its test credential had quota one. The requested
  unapproved model was replaced with Gemini, the next request returned 429,
  another credential returned 403, and embeddings returned 404.
- The disposable service stopped and its test database was removed. No fake
  tenant, grant or payment was inserted in the production database.
- A clean tenant-image container reached the production gateway's health route
  over the Docker bridge after the narrow firewall rule was added.
- The gateway service user cannot read controller `runtime.json`; the service
  uses ProtectSystem=strict, ProtectHome, no capabilities and NoNewPrivileges.

The first activation automatically rolled back because systemd's root:root
0440 credential mount was rejected by an overly strict check. The loader now
allows this systemd read-only mode, while rejecting world access and group
write/execute. Protected failed-activation snapshots are retained.

## Recovery and limits

Protected snapshots are under the controller's `private/gateway-activation-*`.
For gateway-only recovery, stop the gateway; do not restore an old controller
database. The production controller can keep running without the gateway.
The temporary test interface on 18735 is not left running or opened in UFW.

Before rolling the controller back to the historical independent instance,
stop/disable the gateway first. `unify_controller.py --rollback` now rejects
rollback with a live gateway and reads the current DB path from private
runtime configuration rather than copying the obsolete pre-gateway DB.
Preserve latest business state and the original Fernet key. The historical
v0.5.0 upgrade script refuses to run against the shared gateway deployment.

Gateway health means the local service is alive; it is not continuous proof
that the external provider is healthy. No uptime monitor was added.

Worker is not enabled. Its current provider template still assumes both chat
and embeddings; it needs a reviewed chat-only template path or separately
approved embeddings before provisioning. Real Managed Bots, tenant isolation
and lifecycle acceptance remain pending. Formal purchases, AI group chat and
the retired collector remain disabled. Production AstrBot itself still runs as
root; this deployment hardens the gateway, not the entire shared production
process.
