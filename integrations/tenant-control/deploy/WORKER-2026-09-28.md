# Worker and trial delivery readiness: 2026-09-28

## Active services

`astrbot-tenant-worker.service` is enabled and running as `astrworker`, primary
group `astrtenant-state`, supplementary group `docker`. It receives the original
Fernet key via systemd LoadCredential and shares the authoritative business DB
at `/var/lib/astrbot-tenant-state/control.db`.

Tenant data and backups live in `/var/lib/astrbot-tenants`. The Worker-only
AstrBot import state lives in `/var/lib/astrbot-tenant-worker`; importing core
defaults must not write to the production working directory.

The reviewed template is `/opt/astrbot-runtime/tenant-source`. It contains
Superbot Python modules, schema/metadata/docs and explicitly allowed static
images/fonts, not production plugin databases, group configuration or balances.
Worker uses the existing content-addressed tenant image recorded in
`TRIAL-READINESS-2026-09-28.md`.

Worker's unit hides production data and the model gateway credential directory,
uses ProtectSystem=strict, no ambient capabilities and NoNewPrivileges.
Docker socket access is still host-level privilege: these service restrictions
do not turn a Docker-capable Worker into an untrusted sandbox. Production
AstrBot continues running as root; that separate hardening task is not complete.

## Tenant behavior

- Chat-only provider templates accept an empty embedding ID. The approved
  Gemini model is routed through the private gateway with a per-tenant key.
- The new `chat_only_tenant` Superbot option defaults false and is valid only on
  `tenant-*` platform IDs. It creates no knowledge base or embedding requests.
- Its dedicated configuration has no global AstrBot administrators, no builtin
  commands, no knowledge bindings, no automatic cron tools and no WebUI.
  Superbot's own owner and delegated permission checks remain authoritative.
- The original production Superbot configuration was not changed or reloaded.
  Source changes add an opt-in branch; the existing embedding-backed path remains.
- Each tenant container has its own data mount, no published ports, no Docker
  socket, a non-root Worker UID, `--cap-drop ALL`, no-new-privileges, 1 CPU,
  1 GiB memory and a 128-process limit.
- Tenant health now requires the Superbot plugin to be loaded and attached to
  the same running Telegram application, not merely a polling transport.
- Resume, restore and upgrade wait for fresh health before declaring success.
  Rollback stops the new process before moving old data back.
- Interrupted jobs/operations are marked `needs_review` at Worker startup,
  rather than automatically replayed.

## Verified so far

Two offline, disposable tenant-image containers were started with separate
temporary databases and owner identities. Both loaded Superbot, created their
profiles, disabled WebUI, and ran without a traceback. Their proxy keys differed,
their owner settings differed, neither loaded the controller plugin, and backup
directories were generated independently. Containers and fixture databases were
removed afterward; no fake tenant was inserted into production.

Initial smoke testing caught omitted static avatar assets; the template
allowlist was corrected before successful reruns.

A separate systemd-run check exercised `_prepare` as the actual `astrworker`
user with production data inaccessible. It generated the isolated template
successfully. Unit tests cover no-embedding profile creation, route conflicts,
privilege tampering, delayed resume health and failed business-plugin health.
Existing Superbot tests were rerun against the unchanged default branch.

## Real delivery gate

Two two-day trial proposals were sent to administrator 1000000001 for accounts
1000000002 and 1000000003. No grant was confirmed at the time of this report.
The proposals are actor-bound, single-use and expire five minutes after issue.
To obtain fresh confirmations, the administrator can privately send:

```text
/admintrial 1000000002 2
/admintrial 1000000003 2
```

After each confirmation is accepted, the operator may run:

```sh
/opt/telegram-chat-collector-prod/.venv/bin/python deploy/create_acceptance_bots.py
```

That script creates only for owners with confirmed grants while Worker is
ready; unconfirmed owners are skipped. It checks the two existing user sessions under locks, verifies
VIP_dhbot's numeric identity, and records an intent before the Telegram
Managed Bot creation request. An uncertain creation call is never repeated
automatically. It does not collect group messages or resume the collector.

The subsequent live single-tenant acceptance is recorded in
`LIVE-TENANT-2026-09-28.md`. The first account's grant and the two-real-tenant
isolation checks remain pending. Group admission still
requires the group owner to manually add the newly created Bot; no invitations
or group messages were sent.
