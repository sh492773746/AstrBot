# 广告维护 v1.3

## 日常操作

审核订单默认显示已付款待处理，可切换未付款、展示中、待核查。未发布订单本人或广告管理员可在订单页选择“取消订单／退款”：余额付款原路退广告余额，人工核款登记人工退款待处理，测试免付款不退款。人工退款完成后由管理员登记实际金额、时间和流水依据，不执行链上转账。展示中仅管理员可停止，不自动按剩余期限退款。

付款不等于立即发布。满位或篇幅不足按付款及审核就绪时间排队，订单显示原因。后续订单不插队；排队期间可取消未发布订单。新广告从成功完成发布和置顶时计算展示期，续期保持原位置。跨到期边界先处理已就绪续期；已经撤下的广告重新排队，恢复后开始新期限。

广告管理新增“广告栏容量”：每个群／频道统一设置1—100个位置。迁移容量取原名额最大值与实际占用数的较大值。调低不撤下现有展示。编号保持稳定，不随前面的广告到期重新编号；整条消息仍受3900个UTF-16单元限制。

## 待核查恢复

发送、编辑、置顶和取消置顶分别记录完成步骤。Telegram明确限流会保留进度等待重试，未知结果不会自动重发。其他目标继续运行。

进入“待核查广告栏”查看目标、订单、消息链接、前后文案及错误。机器人不能读取任意历史消息，管理员须在Telegram人工核对：

- 已达到预期：点“人工核实已完成”，填写同一条消息ID，再确认。若原消息ID已知，不允许改成另一条。
- 未生效且已恢复原状：先人工确认原正文和置顶已恢复；本次新消息不存在或已被移除，再确认恢复。只恢复本地订单，待发布订单撤销审核，必须重新审核才发布。
- 无法确认：保持冻结。旧版本没有操作快照的冻结记录需维护人员结合审计处理，界面不会猜测恢复。

恢复操作保存操作者和人工确认审计，不伪装为Telegram独立验证。切勿为解锁而直接改数据库状态。

## 充值扫描

每次任务最多处理20页；固定窗口与分页游标持久保存，下一轮继续。普通扫描按6小时推进，重叠24小时；追平后每天回扫最近7天。分页游标失效时重扫同一个固定窗口，不跳过窗口。交易ID和流水键去重。

过期充值单不再阻塞扫描；实际链上时间在订单有效期内的迟到索引可正常匹配。超时转账或金额不符进入充值核查列表，不猜测归属。发现超过重叠窗口的延迟索引保留警示。扫描积压或失败时暂停生成新充值单，已存在订单继续核验。

## 升级与回滚

停止插件前确认没有发送、编辑、置顶、取消置顶正在执行；备份完整插件、配置及SQLite一致性快照。使用AstrBot插件停用入口结束任务，再复制代码、执行增量迁移、重新启用。其他机器人服务保持运行。

新增字段：订单版本、付款来源、退款状态、首次展示、就绪时间、位置号及广告位键；新增目标容量和操作日志表。迁移可重复执行。旧订单金额、价格快照、消息和有效期保留；历史首次展示时间只能从已有记录估计，不用于重新计算期限。测试付款通过原审计识别。

回滚必须先停用插件，保留新增表、订单和流水。v1.2不能理解新版取消／退款／执行日志：有新记录时不得直接恢复旧任务，否则可能重复操作或破坏共享置顶。可恢复旧代码供诊断，但插件保持停用，完成状态兼容适配与模拟检查后才能重新启用。禁止恢复整库覆盖上线后数据。

验证为隔离数据库、模拟Telegram和模拟TronGrid；生产仅核对连接、权限和状态，不自动发送广告。日志仅记录错误类型、操作和目标标识，不输出Token、API密钥。
