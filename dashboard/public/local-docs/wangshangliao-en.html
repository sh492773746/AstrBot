Login And Identity

Create/select a bot, complete password/SMS login and device verification, and save within the ten-minute login transaction. Public group activation uses group control, not login-page selection as an authorization shortcut. Authentication, saved configuration and an online NIM connection are separate states. Empty enabled groups disable group handling, not necessarily private chat. Disable-and-save retains recovery credentials; logout removes them but not ledgers. Re-login creates temporary authentication first; successful save replaces the old connection for the same account. A different account needs a new instance. Stop old automation before migration.

With official 3.7.3 authentication, enter the secondary security code only in the authenticated Dashboard field when the provider requests it. It is never saved or requested in chat. No field is shown when verification is not required. Provider 1400 means the code is not set; 1402 means this sign-in is not yet verified. Incorrect code 1403 requires at least a 30-second wait; 1404 requires checking the lock in the official app, and 1405 requires binding a phone. After successful verification, failed messaging setup can be retried without resubmitting the code. Uncertain verification stops retries and requires a fresh login. Do not disclose the code in logs, screenshots or chat.

Successful security verification does not require credential rotation. Prefer the response header, then a credential in the success body; if neither supplies a new credential, retain this login's credential and fetch the IM token. Absent or unchanged credentials do not imply an incorrect security code. Explicit rejection, malformed receipts and uncertain transport still stop without resubmitting the code. A verified IM token is required before saving completed authentication.

Current password and SMS login requests include version, appVersion and appHash from the verified release, not just updated headers. Release 3.7.3 has version code 335. A changed release requires new verification; do not guess its code from the filename or reuse an old package digest. Official code 1001 is a generic error, not proof of an incorrect password, an account ban or a security code error. The Dashboard retains the numeric code without logging raw provider responses or credentials and does not automatically retry login. Offline tests do not establish successful real-account authentication.

The login panel's business-running/paused badge and enabled-group count follow the instance's runtime business state, not transport-only login configuration. Unavailable runtime status is shown as unverified rather than falsely paused. The panel also shows a connection reason and next step. Missing connection state or group counts stay unavailable rather than becoming "stopped" or zero. The error-details entry labels historical records explicitly: records can remain after recovery and do not establish a current outage. Unknown errors use fixed messages, never raw provider responses.

Phone And Bot Sign-Ins

Running on a server does not make an Android login a desktop login. The client's device classes identify desktop as 1 and Android as 3. Android 3.7.3 uses Android-specific device, client and signing bindings. A phone sign-in may invalidate it; this is not proof that official desktop/phone coexistence was removed.

The desktop 2.8.3 compatibility branch follows the published desktop signing version, device and client identifiers, current get-nim-token route and stable IM device ID. It still verifies the server's bound login token and any required secondary verification. It neither relabels Android credentials nor fabricates Android installation hashes.

IM connections preserve the token endpoint's static, dynamic or callback authentication mode. Callback tokens are not sent as static tokens. Unknown modes fail closed without falling back to a static token; diagnostics never include tokens or raw authentication responses. Legacy replies without a mode retain static compatibility.

After an operator selects the new-login protocol, a new Dashboard sign-in and save are required. Saved Android, legacy and desktop sessions restore their own protocols. Deployment changes and restarts do not convert credentials, reset device IDs, automatically sign in again or delete ledgers. Offline desktop tests are not live coexistence acceptance: a successful fresh sign-in and business reads after another phone sign-in remain necessary evidence.

Connectivity, group-list reads, complete member reads and enabled business scope are separate checks. Member-read failures no longer all say the public service is disconnected: fixed notices distinguish identity conflicts, incomplete rosters, size limits, provider rejection, security verification and rate limits. Diagnostics use AstrBot's native logger without payloads or credentials. Partial rosters never authorize management or settlement, and reads are not blindly retried.

Runtime receive_health separates unhandled non-chat packets, invalid packets, decode failures and unsupported message formats. decode_reasons contains only fixed processing stages, never plaintext, ciphertext, keys or raw responses. Non-chat packets no longer increment unsupported_pushes; they retain a separate counter without claiming support. The login panel warns only on actual decode failures. Counters cover the current run; old aggregate totals cannot be retroactively assigned to these categories. decoded_messages counts actual successful decodes. Bounded decode_shapes summarize field numbers and wire types only, never field values.

Reception supports legacy envelopes and the official 3.7.3 MessagePacket version 1. Both the metadata AEAD and inner message AEAD must pass; packet metadata cannot confer identity or permissions. A zero compression marker still requires authentication and routing checks, never plaintext trust. Unknown packet versions, nested packets and either authentication failure are rejected. The ordinary-message 1 MiB limit is unchanged. The integer wire variants accepted by the official codec are normalized before authentication; conflicting encodings of the same field are rejected. Live traffic still includes envelopes without authentication fields. They remain rejected and cannot reach moderation, AI or settlement. Full compatibility is not claimed; further support requires trustworthy format evidence.

Friend approval reconciliation reads current applications and resolves uncertain attempts before a version-checked resume. Failed reads or unresolved attempts keep the hold, without resubmitting approval. Login recovery does not migrate cashback collection, grant financial authority, enable production groups or confirm a provider hard budget.
