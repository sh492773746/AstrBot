Runtime Logs and Business Audits

The adapter and moderation plugin use AstrBot's native logging pipeline. The standalone cashier forwards HTTP failures, asynchronous-task failures and process startup errors over the existing same-owner, mode-0600 financial Unix socket to AstrBot's logger, live dashboard logs and configured log file. /v1/diagnostics accepts versioned fixed fields, not arbitrary log text, headers, cookies, tokens, request URLs or tracebacks. It grants no financial permissions and adds no public endpoint.

The sender buffers at most128 records and sends batches of at most16 off the HTTP path; the receiver accepts at most64 records/second. Overflow is summarized. Failed or unknown deliveries are not retried. When AstrBot is unavailable, sanitized records fall back to the systemd journal, not another log file. Forced process termination, kernel and systemd errors still require system logs and cannot be guaranteed to reach the dashboard. Ledger, authorization, plan and payment audits remain in their original databases and are never replaced or cleared by runtime logging.

Local root-run test/maintenance CLIs should use the per-command prefix env ASTRBOT_DISABLE_FILE_LOGGING=1 before importing AstrBot. It disables only that process's initial file sinks, retaining AstrBot's same logger and console; it is not a second logging system or a service logging change. Never set it globally.
